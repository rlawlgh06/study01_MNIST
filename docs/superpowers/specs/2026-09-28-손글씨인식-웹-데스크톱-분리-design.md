# 손글씨 인식기 웹/데스크톱 분리 설계

작성일: 2026-09-28

## 1. 목표

하나의 MNIST CNN 모델을 두 가지 형태로 제공한다.

- **데스크톱 버전** (`desktop_version/`) — PyTorch로 **학습**하고, Tkinter 그림판으로 로컬 인식.
  모델 가중치의 유일한 출처(single source of truth)다.
- **웹 버전** (`web_version/`) — **외부 라이브러리 없이 순수 자바스크립트로 추론**만 수행.
  GitHub Pages에 정적 파일로 배포된다. 학습 기능은 없다.

**최우선 제약: 두 버전은 같은 입력에 같은 숫자를 예측해야 한다.** 웹 버전은 데스크톱이
학습한 가중치를 그대로 쓰고, 전처리 파이프라인도 단계·수치·반올림까지 동일하게 맞춘다.
이 동일성은 추측이 아니라 자동 검증으로 증명한다(8절).

### 범위에서 제외 (YAGNI)

- 브라우저 내 학습 / 파인튜닝
- 여러 숫자 동시 인식, 문자·한글 인식
- 모델 양자화·경량화 (float32 그대로 사용, 3절 참조)
- 서버 · 백엔드 API (정적 호스팅만)

## 6. 추론 명세 (`모델.js`)

`desktop_version/model.py`의 `숫자인식CNN.forward`와 같은 순서. **드롭아웃은 추론이므로
건너뛴다** (데스크톱도 `모델.eval()`로 끈다).

| 단계 | 연산 | 출력 모양 |
| --- | --- | --- |
| 1 | 합성곱1: 1→32채널, 3×3, stride 1, 패딩 없음 | 32 × 26 × 26 |
| 2 | ReLU | 동일 |
| 3 | 합성곱2: 32→64채널, 3×3, stride 1, 패딩 없음 | 64 × 24 × 24 |
| 4 | ReLU | 동일 |
| 5 | 맥스풀링 2×2, stride 2 | 64 × 12 × 12 |
| 6 | 평탄화 (드롭아웃1 생략) | 9216 |
| 7 | 완전연결1 + ReLU | 128 |
| 8 | 완전연결2 (드롭아웃2 생략) | 10 (로짓) |
| 9 | 소프트맥스 (최대값 차감 후 지수) | 10 (확률) |

### 메모리 배치 (PyTorch와 반드시 일치)

- 합성곱 가중치 `[출력채널, 입력채널, 3, 3]` 행 우선:
  `W[((출 * 입력채널수 + 입) * 3 + ky) * 3 + kx]`
- 특징맵 `[채널, y, x]` 행 우선: `특징[(c * 세로 + y) * 가로 + x]`
- 평탄화는 `flatten(1)`과 같은 순서: 색인 = `c * 144 + y * 12 + x`
- 완전연결 가중치 `[출력, 입력]` 행 우선: `출력[j] = Σ W[j * 입력수 + i] * 입력[i] + b[j]`

평탄화 순서를 틀리면 정확도만 떨어지고 오류는 나지 않는다. 고정표본 대조가 이 실수를 잡는다.

## 7. 전처리 명세 (`전처리.js`, `리샘플.js`)

`desktop_version/draw_predict.py`의 `MNIST_형식으로_변환`과 단계·반올림까지 동일하게 맞춘다.

### 캔버스 픽셀 → 회색조 바이트

`전처리.js`는 회색조 바이트 배열을 받는다. 그 배열을 만드는 규칙은 `그림판.js`가 지킨다.

- 모델용 캔버스는 **처음과 지울 때마다 흰색(`#ffffff`)으로 가득 채운다.** 캔버스의 기본값은
  투명(알파 0)이고, 투명 픽셀의 RGB는 0이라 그대로 읽으면 배경이 검은색으로 해석된다.
- 붓은 순수 검정(`#000000`)만 쓰므로 `getImageData`의 R·G·B가 항상 같다.
  따라서 **R 채널을 그대로 회색조 값으로 쓴다** (밝기 재계산 불필요).

### 변환 단계

1. **반전** — 그림판은 흰 배경·검은 글씨, MNIST는 검은 배경·흰 글씨: `값 = 255 - 회색조`
2. **글씨영역 찾기** — PIL `getbbox()`와 동일하게 **0이 아닌 픽셀의 최소 사각형**.
   모두 0이면 `null` 반환 (빈 그림)
3. **자르기** — 그 사각형만 남김
4. **축소** — 가로세로 비율 유지, `비율 = 20 / max(가로, 세로)`,
   `새길이 = max(1, round(길이 * 비율))`, **PIL LANCZOS**로 축소
5. **중앙 배치** — 28×28 값 0 도화지에 `((28-새가로)>>1, (28-새세로)>>1)` 위치로 붙임
6. **무게중심 정렬** — 픽셀값을 가중치로 무게중심 `(중심x, 중심y)`을 구하고,
   `이동 = round(13.5 - 중심)` **정수 픽셀만큼** 평행이동, 빈 자리는 0
7. **정규화** — `(값 / 255 - 0.1307) / 0.3081`

**중요**: 4~6단계의 중간값은 데스크톱과 같이 **uint8로 유지**한다. 데스크톱은 PIL 이미지를
거치며 값이 uint8로 반올림되고, 그 반올림된 값으로 무게중심을 계산한다. JS가 float로
유지하면 무게중심이 미세하게 달라져 6단계의 `round`가 1픽셀 튀고, 결과가 크게 갈릴 수 있다.

### PIL LANCZOS 재현 (`리샘플.js`)

PIL은 **가로 패스 → uint8로 클립 → 세로 패스**의 2단계 분리 필터를 쓴다. 각 패스의 계수는:

```
배율      = 입력크기 / 출력크기
필터배율  = max(1, 배율)
지지폭    = 3.0 * 필터배율                 # Lanczos-3
출력 xx 에 대해:
    중심 = (xx + 0.5) * 배율
    xmin = clamp(floor(중심 - 지지폭), 0, 입력크기)
    xmax = clamp(ceil (중심 + 지지폭), 0, 입력크기)
    w[x] = 란초스((x + xmin - 중심 + 0.5) / 필터배율)   # x = 0..xmax-xmin-1
    w 를 합이 1이 되도록 정규화
```

`란초스(x)`는 절대값이 3보다 작을 때 `sinc(x) * sinc(x/3)`, 그 밖은 0, `x == 0`이면 1.
`sinc(x) = sin(파이 * x) / (파이 * x)`.

8비트 경로의 고정소수점 처리까지 재현한다(`PRECISION_BITS = 22`):

```
정수계수 = trunc(w * 2^22 + (w 가 음수면 -0.5, 아니면 +0.5))
누적   = 2^21                                        # 반올림 보정
누적  += 입력[x + xmin] * 정수계수[x] 의 합
출력   = clamp(floor(누적 / 2^22), 0, 255)
```

JS에서는 값이 2^31을 넘을 수 있는 `>>` 대신 `Math.floor(누적 / 4194304)`를 쓴다
(음수에서도 산술 우측 시프트와 같은 결과를 준다).

**리스크와 대응**: PIL 내부 반올림이 위 재현과 어긋나면 완전 일치가 깨진다. 그때는
허용오차를 `1/255 이하`로 낮추고 **그 사실을 이 문서와 `CLAUDE.md`에 기록**한다.
결과를 통과한 것처럼 보고하지 않는다.

| --- | --- | --- |
| **리샘플** | 작은 회색조 입력(가로·세로·바이트 base64)과 PIL이 LANCZOS로 축소한 기대 출력 몇 쌍. 정사각·세로긴·가로긴 경우를 포함 | `리샘플.js` |
| **전처리** | MNIST 5개를 112×112로 NEAREST 확대·반전한 "그림판 모사" 회색조 이미지(base64) + 데스크톱 `MNIST_형식으로_변환`이 낸 28×28 uint8 결과 + 그때의 예측 숫자 | `전처리.js` + `리샘플.js` |
| **모델** | MNIST 평가셋 20개의 정규화된 28×28 입력(base64 float32) + PyTorch가 낸 로짓 10개 + 예측 숫자 | `모델.js` |

이미지·배열은 JSON 비대화를 막기 위해 **base64**로 싣는다. 예상 용량 약 100~150KB.

### 통과 기준

| 검사 | 기준 |
| --- | --- |
| 리샘플 | 출력 바이트 **완전 일치**. (7절의 대응이 필요하면 `1/255 이하`로 완화하고 문서에 기록) |
| 전처리 | 28×28 uint8 **완전 일치** |
| 모델 | 로짓 최대 절대 오차 `1e-3 이하` **그리고** argmax 일치 (부동소수 누적 순서 차이만 허용) |

`자가진단.html`은 세 검사를 돌려 표본별 통과/실패와 최대 오차를 표로 출력하고, 마지막에
`전체 통과` / `N건 실패`를 크게 표시한다. 실패 시에는 어느 표본의 어느 색인이 얼마나
틀렸는지 보여 준다 — 그냥 "실패"만 띄우면 디버깅에 쓸모가 없다.

`테스트/전체검사.js`는 브라우저와 Node 양쪽에서 호출되도록 순수 함수로 두고, 고정표본을
인자로 받는다. Node 설치 후에는 `node 테스트/전체검사.js` 형태의 진입점만 얇게 추가하면 된다.

### 개발 순서 (TDD)

각 모듈은 **먼저 고정표본으로 실패하는 검사를 확인**하고 구현한다. 순서:
`리샘플.js` → `전처리.js` → `모델.js` → (UI). UI는 계산부가 전부 통과한 뒤에 붙인다.

## 9. 실행 · 배포

### 로컬 확인

`fetch`와 ES 모듈 모두 `file://`에서 막히므로 HTTP 서버가 필요하다.

```
cd web_version
py -m http.server 8000
# http://localhost:8000/                  앱
# http://localhost:8000/자가진단.html      검증
```

### GitHub Pages

`.github/workflows/deploy.yml` — `main` 푸시와 수동 실행(`workflow_dispatch`)에서 동작.

- `actions/checkout` → `actions/configure-pages` →
  `actions/upload-pages-artifact` (`path: web_version`) → `actions/deploy-pages`
- 권한: `contents: read`, `pages: write`, `id-token: write`
- `actions/upload-pages-artifact`는 Jekyll을 거치지 않으므로 `.nojekyll`은 불필요

기본 브랜치는 `main`으로 초기화했다(git 기본값 `master`가 아님).

### 모든 경로는 상대 경로

Pages는 `https://<사용자>.github.io/<저장소>/` 하위에 서빙되므로, HTML·JS·CSS·fetch의
모든 경로에 선행 `/`를 쓰지 않는다. 가중치는 `model/weights.json`처럼 참조한다.

## 11. 화면 구성 (`index.html`)

데스크톱 창 배치를 그대로 옮긴다. 왼쪽 그림판, 오른쪽 결과.

- **왼쪽**: "여기에 숫자를 크게 쓰세요" 안내, 280×280 캔버스, `[인식하기]` `[지우기]` 버튼
- **오른쪽**: 큰 예측 숫자, 확신도, 0~9 확률 막대 10개(예측 숫자만 진한 색),
  그리고 **모델이 실제로 본 28×28 미리보기** (데스크톱에는 없는 추가 요소 — 왜 틀렸는지
  바로 보이므로 교육·디버깅에 유용하다)
- 조작: 마우스를 떼면 자동 인식(데스크톱과 동일), `Enter` 다시 인식, `C` 지우기

### 캔버스 두 장 구조

데스크톱이 Tkinter Canvas(화면)와 PIL 이미지(모델 입력)를 나란히 그리는 것과 같은 구조로
캔버스를 두 장 쓴다.

| 캔버스 | 백킹 스토어 | 용도 |
| --- | --- | --- |
| 화면용 | `280 × devicePixelRatio` (`ctx.scale(DPR, DPR)`) | 고해상도 화면에서 선명하게 |
| 모델용 (숨김) | **280 × 280 고정** | `getImageData`로 읽어 전처리 → 데스크톱과 같은 기하 |

같은 선 좌표(280 좌표계)를 두 캔버스에 그린다. 모델용을 DPR로 키우면 붓 두께 대비 해상도가
달라져 데스크톱과 결과가 갈리므로 **고정 280을 유지**한다.

### 붓과 입력

- 붓 두께 20, 둥근 끝(`lineCap`/`lineJoin` = `round`) — 데스크톱 `붓두께 = 20`과 동일
- 누른 자리에 점 하나만 찍어도 보이도록 `pointerdown`에서 반지름 10짜리 원을 먼저 그린다
  (데스크톱 `그리기_시작`의 `ellipse`와 대응)
- **포인터 이벤트**(`pointerdown`/`move`/`up`)로 마우스·터치·펜을 한 경로로 처리
- 캔버스에 `touch-action: none` — 모바일에서 그리는 중 화면이 스크롤되지 않게
- 좁은 화면에서는 두 열이 위아래로 쌓이도록 반응형 배치

### 알려진 차이: 선 안티앨리어싱

PIL `ImageDraw.line`은 계단식(안티앨리어싱 없음)으로 그리지만 캔버스 `stroke`는
가장자리를 부드럽게 칠한다. 따라서 **사람이 손으로 그린 같은 모양이라도 두 버전의
입력 픽셀은 가장자리에서 조금 다르다.** 이것은 이 설계에서 해소하지 않는 의도된 차이다.

- 검증(8절)은 "같은 입력 이미지가 주어졌을 때" 파이프라인이 일치하는지를 본다.
  이 차이는 그 검증을 흔들지 않는다.
- 붓이 20px로 두꺼워 가장자리 한 겹의 차이는 20px→20px 축소 과정에서 거의 사라진다.
- 따라서 **"픽셀 단위로 동일"이 아니라 "같은 숫자를 예측"을 보장 범위로 삼는다.**
  완료 기준 3번의 육안 비교가 이것을 확인하는 자리다.

## 13. 완료 기준

1. `web_version/자가진단.html`의 리샘플·전처리·모델 검사가 **전부 통과**한다
   (통과 화면을 실제로 확인한다. 리샘플에 허용오차를 쓴 경우 그 사실을 문서에 남긴다).
2. `py -m http.server`로 띄운 앱에서 마우스로 숫자를 쓰면 예측 숫자·확신도·확률 막대·
   28×28 미리보기가 모두 표시된다.
3. 같은 숫자를 데스크톱 `py draw_predict.py`와 웹에서 각각 써 보고 결과를 비교한다.
4. 가중치 파일을 일부러 지우거나 `file://`로 열었을 때 10절의 안내가 뜬다.
5. 좁은 폭(모바일 크기)에서 배치가 깨지지 않고 터치로 그릴 수 있다.
6. `CLAUDE.md` 3개, `.github/workflows/deploy.yml`이 존재하고
   `desktop_version/README.md`의 명령이 `py`로 수정되어 있다.
7. 저장소가 커밋되어 있고 `data/`(64MB)와 `__pycache__/`는 추적되지 않는다.
